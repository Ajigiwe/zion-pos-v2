# PHP POS Replacement — Build Plan

Replaces the Flutter (`client/`) offline-native app with a **Laravel 11 web application**.

## 1. Locked Decisions

| Decision | Choice |
|---|---|
| Stack | Laravel 11 (PHP 8.2+, Composer) |
| Database | MySQL 8 (dev on XAMPP, prod on VPS) |
| Architecture | **Online-first**, PWA with IndexedDB offline fallback for till-critical flows |
| Auth/RBAC | Session auth + `spatie/laravel-permission` (Superadmin / Admin / Cashier) |
| Client | Blade + Alpine.js (server-rendered POS screens, no SPA framework) |
| Deployment | Shared cPanel: MySQL via cPanel UI, docroot = `server/public`, cron via cPanel, AutoSSL (see `server/deploy/DEPLOYMENT.md`) |
| Disposition of `client/` | Feature-freeze, run in parallel for parity, scrap after cutover |

## 2. Architecture Shift (vs. Flutter app)

```
Flutter (offline-first, LAN host/client sync)      Laravel (online-first, PWA fallback)
─────────────────────────────────────────          ─────────────────────────────────────
SQLite per station                    →            One central MySQL
LAN sync engine (handshake/push/pull) →            HTTP to VPS; offline = queued IndexedDB ops
Drift + riverpod                      →            Eloquent + Blade/Alpine
Desktop installer (Inno Setup)        →            HTTPS in browser (PWA installable)
WorkstationConfig per till            →            "Till name" is just a login-time setting
```

What the central-DB model **deletes outright**: `lan_database_server.dart` (579 LOC), `lan_sync_service.dart` (551 LOC), `lan_database_client.dart`, `sync_schema.dart`, `workstation_config.dart` and all sync-queue triggers — roughly 2,000 LOC of the hardest code that no longer needs writing.

## 3. Offline Fallback Contract

**Tiered, by flow:**

| Tier | Flows | Offline behavior |
|---|---|---|
| 1 — Offline-first | Sales, refunds | Full queue: UUID idempotency keys, IndexedDB outbox, auto-flush on reconnect. Price/stock snapshots cached at login and refreshed every 5 min while online. |
| 2 — Degraded | Catalog edits, low-stock checks | Read-only from cache; writes blocked with a clear banner |
| 3 — Online-only | Imports, reports, user management, settings, inventory adjustments, dashboard | Blocked offline with an explicit notice |

**Sync rules:**
- Every offline sale carries an `idempotency_key` (UUIDv4); `POST /api/sales` dedupes on it — retries are always safe.
- **Oversell policy**: offline sales may oversell; the server accepts them and writes a flagged negative adjustment for admin review (same push-wins philosophy as the current `LanSyncService`).
- Cheap reconciliation: the server returns the canonical row + stock delta after each accepted record; the client updates its snapshot and requests a full refresh when drift grows too large.

## 4. RBAC

| Role | Powers |
|---|---|
| **superadmin** | Everything + user/role management, settings, audit-log export |
| **admin** | Catalog, inventory, refund approval, reports, imports |
| **cashier** | POS screen, own-shift sales, refund requests (needs admin approval) |

Permissions live in `spatie` tables, seeded at boot. Every mutation writes to the audit log (ports `AuditLogs`).

## 5. Data Model (Drift schema v8 → Eloquent)

Tables ported ~1:1:

`users · roles/permissions (spatie) · categories · brands · suppliers · products · stock_movements · sales · sale_items · payments · refunds · refund_items · exchanges · audit_logs · import_batches · settings`

Additions:
- `idempotency_key` (unique) on sales and refunds
- `till_id` on sales (replaces workstation identity)
- `uuid` on rows that offline clients create
- standard soft-deletes

Domain rules to preserve (from `client/lib/core/database/tables.dart` and the design doc):
- **Stock is a ledger**: current stock = sum of movements, with a cached column for performance
- **Refunds/exchanges never mutate the original sale** — new transactions only
- **Immutable history**: corrections are new records

Preserved movement types: `OPENING_STOCK, PURCHASE, BULK_IMPORT, SALE, REFUND, EXCHANGE_RETURN, EXCHANGE_SALE, DAMAGE, ADJUSTMENT, TRANSFER`.

## 6. Phases & Estimates

### Phase 0 — Scaffold (½ day)
- New `server/` folder: `laravel new` + Blade/Alpine, `spatie/laravel-permission`, `laravel/sanctum`, `barryvdh/laravel-dompdf`, `maatwebsite/excel`, `vite-plugin-pwa`
- XAMPP vhost pointing at `server/public`, MySQL DB + user, git init, `.env` and CI stub

### Phase 1 — Data model (1–2 days)
- Migrations for all tables, seeders (roles, permissions, the 13 default categories from `_defaultCategories`), model factories for tests

### Phase 2 — Auth + RBAC + admin shell (2 days)
- Login, sessions, password reset, user CRUD, role assignment, audit logging service, sidebar layout with the 9 sections matching `home_shell.dart`

### Phase 3 — Catalog & inventory (3 days)
- Products CRUD, categories/brands/suppliers, stock-movement ledger + movement-type UI, CSV/Excel import writing `import_batches`

### Phase 4 — POS + sales (4–5 days)
- Till UI (cart, keyboard-wedge barcode input — HID scanners already emulate keyboards, so no driver work), mixed payments (cash + mobile-money reference — ports `momo_reference_test`), 80 mm thermal receipt printing via browser print CSS + `dompdf` archive copy, refunds & exchanges flows

### Phase 5 — Offline PWA (3–4 days)
- Service worker + app-shell precache (vite-plugin-pwa), catalog/stock IndexedDB snapshots, outbox queue, sync endpoints + reconciliation, per-tier offline banners, sync-status indicator

### Phase 6 — Reports, dashboard, settings, backups (2–3 days)
- Sales/inventory reports + CSV export, dashboard KPIs and low-stock badge, settings pages, scheduled `mysqldump` backups with offsite upload

### Phase 7 — Data migration (1–2 days)
- ETL: SQLite → JSON → Laravel importer command. Migrates catalog, suppliers, and stock balances (as OPENING_STOCK/ADJUSTMENT movements). **Open decision:** migrate historical sales or keep history archived in the Flutter exports only.

### Phase 8 — Deploy + cutover (2–3 days)
- VPS (nginx, PHP-FPM, MySQL, TLS), cron for scheduler + `queue:work --stop-when-empty`, uptime monitoring
- 1 week dual-run UAT (new POS vs Flutter app), then final SQLite archive and decommission `client/`

**Total: ~3–4 weeks part-time.**

## 7. Risks

| Risk | Mitigation |
|---|---|
| Multi-day connectivity loss at a till | Outbox persists per device; header shows pending count + oldest-item age; manual JSON export/import as an escape hatch |
| Cheapskate shared-hosting quirks | cPanel-native design: `database` cache/session/queue drivers, mysqldump degrades to pure-PHP dump when `exec` is blocked, no queue worker required, phpMyAdmin-importable `schema_seed.sql` |
| Receipt printing reliability | Browser print CSS on 58/80 mm template; keep Flutter printer settings as UI parity task for later |
| Loneliness of a cache gone stale | Till pushes a full catalog refresh when drift exceeds a threshold |
| Data loss on cutover | Flutter SQLite is never deleted — read-only archive; all history exported to PDF/JSON before decommission |
